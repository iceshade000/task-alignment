# 需求对齐与分层执行计划

在大量工作前确认方向，在已批准范围内持续推进，并控制验证与阅读成本。适用于不同领域，不替代领域方法。用户点名时应读取并遵循，不能只回答“已安装”。不为应用本 skill 另建审批文档或对每个操作请求确认。

## 1. 确认顺序与授权边界

新且复杂或模糊的项目默认依次进行，不能自行合并：

1. **需求对齐**：阅读已有材料，解释完整任务的目标、范围、各部分关系、成果要求及关键未知，问清重要歧义，等待用户确认理解。
2. **整体计划确认**：需求确认后，给出整体路径、最终预期成果和完成标准，等待确认；此时不同时提交下一步计划或制作阶段成果。
3. **下一步计划确认**：整体计划获批后，给出本阶段具体行动、预期成果和停止条件，等待确认；不能先产出论证、正文或代码，再用审结果代替审计划。
4. **执行与反馈**：本步获批后持续完成并交付。进入尚未获批的新阶段前，确认其具体计划；不重审未变的需求和整体计划。

确认只对应已展示的内容和当时的问题。只回答语言、篇幅或“由你做”这样的分工选择，不算确认完整需求或未展示的计划。“可以”“继续”若明确回应当前计划即可，无需固定口令；沉默不算确认。“开始干活”“帮我完成”等一般任务指令不表示跳过对齐。

用户明确要求合并或跳过某关，或已有适用内容得到明确确认时，按该授权继续。直接问答和明确的小修改不套用上述启动流程。已有项目从已确认位置继续，不重问已知事项。只有目标、范围、重要规则、交付或明显成本超出约定时才重新确认；只暂停依赖新决定的工作，阶段内不逐个操作或小批次询问。

## 2. 澄清与计划应包含什么

**澄清需求：**区分用户要求、已知事实、自己的假设和真正缺口。关注用途与读者、范围边界、成果形式与深度、资源限制。只问影响结果且现有信息无法回答的问题，用具体例子和选项后果帮助用户决定，不逐项盘问。主动建议影响适用性的质量要求并说明取舍；区分基本可靠性、建议优先级和需确认的硬门槛，不擅自把建议变成筛选限制或额外验证。

**为澄清而探索：**理解任务所需的已有文件、代码、框架和记录可以直接阅读。若仍缺少决定方向的依据，需要新增调研或可行性尝试，先说明具体问题、有限范围和预期决策依据，获确认后探索。根据问题选最直接、成本最低的方式，例如看代码、检查数据样本或查少量权威资料；获得足够依据就停止，回到尚未完成的确认点。探索授权不等于正式项目计划获批。已批准阶段内的普通尝试遵循该阶段授权，不因也叫“探索”而重新申请。

**整体计划要简明：**说明目标与范围、最终会得到什么及其用途、主要阶段、完成标准和关键假设。不要展开全部操作，不把未知发现或效果预设为必然结果。

**下一步计划要具体：**说明本步目标、复用材料与缺口、行动与判断规则、阶段成果，以及准备采用结果时核验什么、到哪里停止。必要时展示字段或成果结构，帮助用户发现偏差；不提前生成实质成果，不罗列工具调用，不编造文件路径。

两种计划按上一节分别确认，都必须说明预期结果，不能只有动作列表；不强制填表。若表达深度或批量规则未定，将代表性样例安排为获批阶段的产出，用一次样例审阅确认内容、结构和可理解程度后批量展开。样例审阅不替代启动确认；已有适用样例直接复用。获准并行时，各执行者沿用同一规则与样例。

## 3. 执行与适量验证

优先复用适用的现有成果，仅补缺口或处理具体过时、错误的部分，不从头重复搜索、下载和提取。不擅自增加范围、交付物或方法复杂度。

**在阶段内先尝试推进，选定有用结果后核验关键依据，再正式采用。**

- 尝试时只做判断可行性所需的最低限度检查。暂定内容可用于草稿，不冒充事实。弃用的尝试不补验证；仍影响后续决定的信息不算弃用。
- 进展是得到计划所需的候选、方案、样例等，不是工具调用量或文件数量。准备正式使用或作为下游依据时，只检查错误会改变决定或使成果失效的部分，不能拖到项目结束才核验已被依赖的前提。
- 优先复用适用的证据和检查结果，采用足够解决疑点的最小检查。通过即停止；无新改动、新证据或具体矛盾不重复检查。失败则修正、限定用途或弃用。没有新信息时不机械重试。
- 无法核实的内容如实限定，不宣称已验证。若必要核验明显超出约定成本或范围，按授权边界反馈，不阻塞无关工作。

判断可行性、避免不可逆错误及明确要求的安全检查仍需前置，不能据此扩展为全面验证。用户认可样例的布局和深度不代表认可事实；可用标明暂定内容的样例讨论表达，但正式采用其结论或据此批量推导前仍需关键核验。

## 4. 从读者视角形成与修改成果

**先选内容，再组织逻辑。** 根据读者背景和当前用途确定每个单元要帮助其理解、判断或完成什么。按读者所需顺序组织，不按探索和对话顺序组织。“执行者为做对必须知道”不等于“读者为读懂必须知道”。先明确各段作用及推进关系，再安排句子的核心内容；后句接住已有对象或问题并增加信息。缺解释就补，位置不当就调整，不能靠抽象过渡或连接词掩盖跳跃。仅对复杂或难懂部分临时拆解句意与关系，不全文逐句标注或另交检查表。

**含义、名称、来源分别处理。** 首次出现的概念、框架、缩写或符号，按读者背景解释是什么、为何需要及与前文的联系，再按识别或指代需要使用名称，消除版本号等明显歧义。仅补全称不等于解释。来源归属与引用按任务要求保留；省去简称不意味着省去提出者、出处或必要解释。已知内容不重复解释；要求覆盖的内容安排适当位置，不因衔接困难直接删除。

**修改信息不漂移。** 具体任务要求和已确认的重要信息优先于简洁、风格建议。局部修改只处理指出的问题与必要衔接；允许改写措辞、调整顺序，但保留仍成立的事实、来源、引用、条件和要求覆盖的内容。理解改变时可重写受影响单元，不用追加否定保留错误框架。发现旧内容错误或与新要求冲突时，指出原因及处理，不因曾确认就保留错误，也不默默删除。需要改变已批准范围或关键判断时才重新确认。

**正文与修改过程分开。** 正式成果保留已确定的知识和依据，不默认包含错误假设、纠偏经过和弃用路径。优先直接介绍主题，必要的辨析、争议和局限放在相关结论附近；不为读者未面对的误解专设反驳，也不机械禁用否定句。修改理由放必要的交付说明，不混入正文；用户要求审计或排错过程时才按该用途呈现。

**降低阅读量，不删必要信息。** 以可理解的完整单元分批或分层呈现，保留必要上下文。简短总览能对应具体例子与依据，区分事实和自己的综合解释；关键依据紧邻表述或可精确定位，额外细节按需查看，不能将必需解释全藏到附件。难懂时缩小单次覆盖范围并补解释，不继续压成术语。已授权工作持续完成，分批阅读不代表分批等批准，也不意味着缩减总交付范围。

上述规则融入写作与修改。交付前只对拟采用内容简短通读：脱离对话能否理解，句段是否连贯，是否丢失必要信息或残留无关纠偏。发现问题就修相应部分，不另设审核流程，不因此重查全部材料。

## 5. 保存与完成

有文件产出时，每项交付物明确一个当前版本，日常修改更新原文件；只保存影响判断、复现或解释的关键中间材料与必要的重大变更快照。不同交付物可有各自文件，不为版本管理反复建目录；被否决的素材退出当前候选，非文件任务不强行落盘。

交付时给清楚的阅读或使用入口，说明成果、与约定的差异、关键核验及剩余限制，不把局部核验称为全面验证。满足约定即完成，不追求消除所有未知，不为每次交付追加工作；确需进入未批准的新阶段时再提出该阶段计划。
